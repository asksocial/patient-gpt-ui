# Gate 2A connector and retention handoff

Gate 2A is the synthetic acquisition baseline for the retention workstream. Use the commit that introduces `202611180004_corpus_acquisition_connector.sql` as the integration baseline. Identify it with `git log -1 --format=%H -- supabase/migrations/202611180004_corpus_acquisition_connector.sql` on the finalized connector lineage. The architecture review and retention test requirements are in [the retention ADR](corpus-acquisition-retention-adr.md).

| Interface | Gate 2A contract | Retention integration |
| --- | --- | --- |
| Mapping registration | Inject `AcquisitionProvider` instances at server composition time. Register each `(provider, ref)` once. `SourceApproval` carries the fingerprint, explicit normalization version, platform, and source and retention policy references. The Apify adapter hashes its canonical mapping plus the normalizer version, including the Actor/build, optional output fields, URL host policy, and author-key version. `corpus_acquisition_approve` persists the digest and normalization version with the immutable plan and validates the approved source and retention policy references against the protocol. | Give changes to output projection or canonical row behavior a new versioned mapping reference. Keep the exact approved adapter and key version available for open work. A missing or mismatched registration places work in `review` before provider I/O. If policy disallows the old shape, hold the work for an approved disposition; preserve old checkpoints. |
| Dataset binding and ownership | After a verified successful run, `advance('bind')` couples its run and dataset IDs to the workspace work item and existing attempt, with collection time, expected rows, and verified cost. The worker checks the pinned Actor/build and exact run ID, uses that run’s default dataset, then checks dataset metadata identity. The bind and attempt update are atomic. | Use this boundary to register scoped provider ownership and per-workspace consumers. The current run/dataset IDs and association establish ingestion provenance. Ownership or deletion authority requires separate, trusted verification of the provider account or project and immutable dataset ID. Failed or cancelled runs may leave datasets the connector never binds. Their discovery and ownership verification require a separate approved path. |
| Claim and resume | `corpus_acquisition_claim` returns due work with a 90-second lease, persisted identifiers, the pinned mapping, and the committed offset. A transition requires the current unexpired token. Managed administrators with workspace write access may resume a reviewed item. Resume keeps its attempt, reservation, cancellation intent and checkpoint, then chooses paging, polling, reconciliation or ready from saved state. | Extend bind, claim/resume, and dataset read authorization to honor durable release state before enabling deletion. A database lease fences transitions. A deletion worker also needs a way to drain in-flight provider reads before an external delete. Preserve lock ordering across workspace and provider-dataset scope. |
| Settlement and reconciliation | Submit intent is committed before the provider POST. An uncertain submission is reconciled using the original work correlation and exact retained Actor input. Unknown or over-budget usage and unresolved runs can enter `review` with the reservation held. `advance('finish')` uses the foundation to atomically settle the attempt and move work to `done`. Successful settlement requires complete checkpoints and the worker checks the final provider row count. A verified callback wakes reconciliation and cannot settle work. | Keep unresolved, resumable or unsettled work as a dependency. Any later abandoned-work disposition needs an auditable settlement with reconciled charges, preserved provenance and a terminal decision on whether data may be discarded. `done` alone supplies no release authority. |
| Durable dataset release eligibility | No ownership registry, release RPC, provider DELETE method or delete worker is available in Gate 2A. Every dataset remains ineligible for deletion under this baseline. | In a later additive migration, define a private registry keyed by `(provider, verified account/project scope, dataset ID)`, with consumer references and a durable release/deletion intent. Under one serialized eligibility transaction, require verified deletion authority, a terminal provider run, reconciled usage, complete or explicitly abandoned ingestion, released consumers, drained reads, and no recovery, reconciliation or hold. Persist intent and block new use before any external call. Confirm deletion or authoritative absence in the verified scope against the same intent. Fail closed on ambiguous scope, unknown dependencies or uncertain outcomes. |

## Replay and authorization invariants

- `corpus_builder_page` owns the `(workspace_id, attempt_id, page_offset)` checkpoint and digest of the normalized JSONB array. Preserve dataset, offset, exact ordered rows, bound collection-time fallback and historical projection. A committed replay can acknowledge the old checkpoint without recreating source content. A lost acknowledgement recovers from the next committed offset. Keep reservation, settlement, and sampling eligibility under the foundation functions.
- `corpusAcquisitionFor(providers, session)` requires a trusted server-side session resolver. Future composition must supply verified actor and principal identity, active managed-account status and administrator status. The database independently checks active managed platform administrator status and workspace membership or ownership, and requires owner/editor access for mutations. Ordinary API roles have no connector RPC grants. Even `service_role` has no direct connector table access.
- Both application flags remain off by default. Gate 2A exposes no browser route, scheduler, default Actor, credential configuration, callback endpoint or deletion transport. The HMAC callback verifier expects a trusted relay; polling works independently of callbacks.

## Acceptance and release boundaries

Use `node --import tsx src/test/runCorpusAcquisitionQuality.ts` for adapter and orchestration fixtures. Use `python3 scripts/test-corpus-acquisition.py --pg-bin <PostgreSQL-17-bin> --postgrest <PostgREST-binary>` for two independent loopback profiles. The harness checks catalog and fixture preservation alongside acquisition, authorization and recovery. It never uses hosted databases or provider credentials.

Final validation passed on PostgreSQL 17.12 and PostgREST 16.6. Both profiles produced schema fingerprint `e702a846ba9eb823c8e4e4a9ed4902f2a6b64c236842b5373db0c35305b856b2` and connector frame fingerprint `220f83ce3a5ddf2a21c657cc2e23f7f3f14be0c493e506d16a41df03e9b9457b`. Migration `202611180004` has SHA-256 `4dc1006d182c54bb6e9020b4c5dab87e8b9dbd9012cf7a310d40857a10ad2d20`. Adapter fixtures, targeted lint, workspace type checking, search, citations, Continuous Intelligence, workspace management, provisioning, Evidence Integrity security/privacy, PV compliance, E2B(R3), and isolated ODCS/operations/identification regressions passed.

The pre-existing Gate 1B server wrapper imports an application provisioning module outside this commit’s tracked baseline. Use the migration and standalone synthetic connector tests for isolated retention work. A full application checkout requires the separately managed provisioning integration. The connector’s server entry point accepts that integration through its trusted session resolver.

To roll back isolated validation, discard the disposable profile and replay through `202611180003`. Keep both flags disabled outside isolated testing. A hosted rollout remains blocked by Gate 1A. Live acquisition separately requires a verified Actor/build, an enforceable provider spending bound, verified usage and pagination semantics, server credential configuration and approved data rights. Revision retention and provider deletions require the ADR approvals and their own migrations and tests.
