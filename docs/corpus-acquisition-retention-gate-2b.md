# Corpus Acquisition retention and exclusive dataset release

The isolated retention branch builds on Gate 2A commit `845a8c4bbcc14f1f016eec5daede48b289761e06`. Apply migrations `202611180005` and `202611180006` after `202611180004`. The two migrations leave the existing Evidence Integrity and PV schemas outside the retention boundary.

## Revision and operational retention

- Use `corpus_builder_expire_revisions` with a workspace, an explicit past or current cutoff, and a batch limit of 1–500. It erases due revision text, observation URLs and author references, and stored derivatives. It records a revision tombstone and a minimal chain event in the same transaction. The source identity, source revision, observations, frames, memberships, and historical manifests still resolve. The existing full-frame evidence availability check excludes expired content even when the expired revision was outside a selected subset.
- `corpus_builder_withdraw` accepts `withdrawn` for a source-wide takedown. Use the new expiry operation for revision retention. Existing deadlines are preserved. New content records carry their protocol retention reference, and reobservation records the stricter policy when that policy shortens the deadline. An old row with unknown policy provenance has a nullable policy reference. No 30-day raw default or retrospective recalculation is applied.
- Corpus revision artifact reads and writes are gated by workspace and current revision availability. Extracts and embedding payloads become inaccessible at the deadline and are physically removed by cleanup. The artifact APIs have no connection to existing vector indexes, exports, or retrieval. Any future derivative or export store must enforce revision lineage and the same read gate before use.
- The new operational log contains only work UUID, phase, failure count, and timestamps. Events expire after 2,160 hours. `corpus_builder_purge_operations` deletes expired rows in bounded workspace batches. The immutable audit chain, callback replay keys, checkpoints, reservations, settlements, and release evidence stay outside that purge. Cleanup requires the existing workspace editor/owner and active managed-platform-admin checks. No automatic scheduler is wired.
- New pages reject unexpected normalized fields at the database boundary. Previously committed pages compare their original digest before the new allowlist, so the stored checkpoint remains authoritative after an acknowledgement is lost or content expires. The approved mapping fingerprint and normalization version still fence provider calls. Already-expired content cannot be inserted or recreated.

## Exclusive dataset and release contract

New acquisition work requires an enrolled provider account and a trusted adapter assertion matching the pinned mapping, immutable dataset ID and run identity. The Apify adapter checks dataset metadata for the designated account ID, exact Actor and run, and restricted access. Database-side enrollment is separate, private, and rollbackable through disabling release. The stored evidence references the approval, verification method and time, responsible attempt, run and dataset. One provider/dataset ID can bind to only one acquisition attempt across workspaces. No enrollment or live Actor is configured by these migrations. Historical bindings have no release authority, and unfinished Gate 2A work can resume without ownership proof while remaining ineligible for release.

A workspace administrator explicitly approves release. The approval records the authorizer and any explicit incomplete-ingestion disposition. Before approval and again before execution, the database requires reconciled terminal work, matching budget settlement, complete or explicitly dispositioned ingestion, the passed bound dataset deadline, active ownership approval, and no pending reader or internal or legal hold. Dataset reads from the connector register before item or final-size requests and close when the request ends. An orphaned reader remains a blocker. Gate 2B has one coordinated internal hold and no external or shared consumers. A future internal consumer must participate in this hold/read contract before it may use provider data.

Only synthetic accounts enrolled in fixture execution mode can exercise execution leases and outcomes. A different administrator in the same workspace claims a fenced lease. Temporary or unknown outcomes retry on the same intent with a delay; repeated failures or denied requests go to review. Completion can report simulated deletion or verified absence, and replaying the same successful acknowledgment is idempotent. The immutable chain records authorizer, execution claims and outcomes separately. There is no provider DELETE transport, fixture runner with network credentials, or external deletion endpoint.

Apify dataset metadata can establish owner and run association. Exclusive organizational control, absence of out-of-band consumers, and authority to delete must come from the account enrollment process and a production verifier. Provider metadata must be rechecked at the point of any future external delete. [Apify dataset metadata](https://docs.apify.com/api/v2/dataset-get)

The replay compared Evidence Integrity and PV catalog definitions and sentinel data before and after the retention migrations. Separate local Evidence Integrity security/privacy, PV compliance, E2B(R3), and ODCS/operations/identification suites passed against the unchanged primary application.

Before any real account can be enrolled or a deletion worker enabled, confirm designated account ownership and restricted access, eliminate out-of-band dataset consumers, designate independent credentials and an execution principal, and approve ownership revalidation and orphaned-reader disposition. Legal and Privacy still need to approve source rights, field retention and time limits, audit/control schedules, legal holds, exports/backups, data-subject requests, provider regions and deletion guarantees. A future scheduler must handle archived workspaces through separately approved privileges. The existing admin cleanup endpoints operate on active workspaces. The separate hosted Gate 1A release blocker remains.
